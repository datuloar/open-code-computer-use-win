# Paint rabbit test: October 24, 2026

A colored rabbit was drawn and saved as a 1536 x 864 PNG in Microsoft Paint using this
repository's real MCP tools. The operator used Paint's oval, line and color controls through
UI Automation and mouse drags. No image was generated elsewhere or imported into the canvas.

The supervising assistant drove the MCP server directly. This was an exploratory task with
repairs during the run, not an autonomous OpenCode model benchmark. Paint was already open
before the first recorded call. The saved image was inspected after saving.

Elapsed time includes reasoning, source edits, inspection and pauses. Tool duration includes
countdowns and backend startup. Neither figure measures model latency alone. Character counts

system instructions and conversation history. They are not token counts.

## Fixes and verification

Paint exposed Oval twice, as a ListItem and a Button. An optional observed `role` now narrows
`find`, `tap`, inspection and conditional waits. Same-role duplicates still refuse selection,
and a disabled exact match cannot redirect input to an enabled substring.

The fill menu used a separate native popup surface. The visibility guard now accepts that
surface when it belongs to the selected control's UIA ancestry. It still refuses a different
window covering the requested control, including a window owned by the same application.
The repaired Paint call selected Solid fill by name; a subsequent observation confirmed that
the menu closed. Providers that expose unrelated identities can still require an observed
coordinate fallback. Matching a process ID alone is not sufficient to permit a click.

Focusing a maximized window previously restored its normal size. Focus now restores only
minimized windows. The desktop suite verifies both behaviors.

In this Paint version, the first canvas interaction after a palette change sometimes restored
focus without creating the expected shape. An empty canvas click followed by a fresh observation
allowed drawing to continue. Enter did not reliably commit the selected shape. This is recorded
as app behavior; successful input delivery alone does not prove a stroke appeared.

desktop checks. The [desktop report](2026-10-24-v1.0.0-opencode.json) records its source fingerprint.
The subsequent output and guidance changes in `6e8f5e7b04c65ff51611e673b83acf927a6065d2` passed
79 unit checks and the [actual OpenCode loopback integration](2026-10-24-v1.0.0-smoke.json).
The loopback fixture verifies tool wiring and loaded instructions, not model decision quality.

## Text overhead

The old 152-character control reminder appeared 125 times and used 19,000 response characters.
It now uses 75 characters while retaining the stop instruction. Substituting that string into
the recorded responses removes 9,625 characters, a 22.4% reduction in this trace's response text.
This is a deterministic text calculation, not a second drawing run or a measured billing saving.

The role argument adds 216 UTF-8 bytes to the tool catalog: 6,666 before, 6,882 after.
Automatic guidance remains below 4,000 bytes and the optional skill below 8,500 bytes.
Those instructions explain dialog targeting, canvas verification and recovering from ambiguous
controls. Their effect on a model's action count needs a provider-backed run.

## OpenCode provider attempts

On October 23, actual OpenCode CLI runs using `opencode/deepseek-v4.1-flash-free` and
`opencode/nemotron-3-ultra-free` both received HTTP 403 `FreeTierError` before their first
model step or desktop action. Neither emitted usage events. Input, output, reasoning, cached
tokens and task cost therefore remain unmeasured. Zero-initialized collector fields must not
be treated as a successful zero-token task.

The next efficiency comparison should use the same starting canvas and task, a working
authorized provider, usage events, the final saved image and repeated trials. This run supports
the specific fixes above; it establishes no task win rate against UI-TARS or other systems.
